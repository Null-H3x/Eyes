## 0. Why this cycle

`eyeforward` lists three remaining hiding places for `C`: a PRNG under an untested
family, **a structured construction in an untested glyph-labeling frame**, and a
non-alphabet source. The second has been carried as open since the restructure and
never attacked.

The reason it is live: **FR28's exclusions are labeling-dependent.** FR28 excluded
affine, power and keyword-mixed alphabets on the repaired skeleton with working
positive controls — but it tested `q[g] = a·g + b` in the *current* base-5 trigram
frame. That frame is a community reading of glyph pictures: three visual features,
five states each. *Which* feature is the most significant digit, and *which* state
means 0, are choices. Relabel the glyphs and it is a different test.

The skeleton itself is relabeling-invariant, so all 384 relations survive any frame
change untouched. Only the algebraic-structure question moves. And a hit would not
yield a pin — it would yield **`C` outright**, testable in microseconds against 384
relations, injectivity and packing, with no language objective required. Low prior,
negligible cost, total payoff. That asymmetry is why it was worth a cycle.

## 1. CHALLENGE I — the search space is 24,000× smaller than I claimed

I estimated the frame group at `S₅ ≀ S₃`, order `6 × 120³ = 10,368,000`. That is the
group, but it is **not the search space**, and the corpus says so.

The corpus uses exactly the labels `{0..82}` — all 83 present, none above, verified
directly. If the engine constructs glyph *i* from the digits of *i* over indices
0…82, then the community's frame can differ from the true one only by a relabeling
that maps `{0..82}` **onto itself**. In trigram space `{0..82}` is not a product set
— it is an irregular initial segment (`d₂ ∈ {0,1,2,3}`, truncated inside `d₂=3`) —
so its stabiliser is small.

Computed exactly:

```
frame group order        10,368,000
STABILISER of {0..82}           432
reduction factor            24,000×
```

**And every one of the 432 has the identity digit-position permutation.** The
corpus's own label contiguity **forces the digit ordering completely**: the
most-significant visual feature is determined, without reference to the pictures.
That is an independent corroboration of the community reading, obtained from the
ciphertext rather than from the glyphs, and it is new.

Only the five-state labelings retain freedom — 432 of them, exhaustively
enumerable. The cycle changes from a sampling problem to a complete sweep.

## 2. Gate

Seven selftests green before corpus contact. Two carry the weight:

- **S5 (positive control):** an affine alphabet planted under a randomly chosen
  frame is recovered, and **exactly one frame fits** — the sweep is not merely
  sensitive, it is discriminating.
- **S6 (negative control):** a random alphabet fits **zero** frames.
- **S4** confirms 379 relations, which is FR53's canonical 384 minus the five
  two-glyph components I do not hold.

All tests run **drift-free**. Within a component `q[g₂] − q[g₁] = drift·(Δ₂ − Δ₁)`,
so for an affine alphabet the ratio `(Δ₂−Δ₁)/(ρ(g₂)−ρ(g₁))` must be constant and the
drift divides out. FR28 had to sweep all 82 drifts; this cycle does not need to,
which is why a 432-frame sweep costs less than FR28's single-frame one did.

## 3. Results — all three families excluded in all 432 frames

| test | result |
|---|---|
| **F1 affine** `q[g] = a·g + b` | **0 frames fit.** Fewest distinct multipliers over all frames: **79** (need 1). Identity frame: 82. |
| **F2 power** `q[g] = g^k` | **0 frame/exponent pairs fit** across all 432 × 81 combinations. |
| **F3 keyword-mixed** (ordered-tail) | max **13** over 432 frames; mean 5.32, sd 2.09, chance expectation 4.57. Identity frame: 4. |

F3's maximum lands **exactly at** the pre-registered threshold of ">13", and
therefore fails it. Thirteen is +3.7 sd on a single frame, but it is the maximum of
432 correlated draws, where the expected maximum is already near +2.9 sd. **Recorded
as a non-finding**, with the threshold honoured as written rather than adjusted after
seeing the number — which is the whole point of registering it.

Note FR28 reported 78 as the fewest distinct multipliers; I get 79 as the minimum
across frames and 82 in the identity frame. The difference is the five two-glyph
components I lack, and the direction is conservative — fewer relations can only make
a fit *easier*, and no fit appears.

## 4. What this buys

**FR28's exclusions are now frame-independent rather than frame-conditional.** That
was the standing caveat on them, and it is discharged. `C` is not generated by a
simple algebraic rule **in any glyph-labeling frame the corpus permits** — not just
in the one the community happened to read.

`eyeforward`'s second hiding place is therefore **closed for algebraic construction**.
It remains open for non-algebraic structured construction, which this cycle does not
touch and which has no obvious test.

**What it does not establish.** A random permutation returns the same verdict on all
three families, so these exclude *structure*, not the corpus. And the whole result is
conditional on two things:

1. **The engine enumerates indices 0…82.** If instead the 83 glyphs are an arbitrary
   subset of a larger constructed set, the label contiguity is a community artifact,
   the stabiliser argument collapses, and the search space returns to 10.4M. That is
   still sweepable, but the digit-ordering result would be lost.
2. **The base-5 trigram reading is the right decomposition at all.** Which is now the
   load-bearing question in this series.

## 5. THE BASE-7 PROBLEM IS NOW LOAD-BEARING

`GHIDRA.md` describes tracing a **base-7** decoder. The corpus is read as **base-5**
trigrams. Both cannot describe the same object.

This mattered mildly before and matters a great deal now. Every number in this cycle
— the group order, the stabiliser of 432, the forced digit ordering — is computed in
the base-5 frame family. If the constructor is base-7, the frame family is the wrong
one and §1–§3 describe a group the glyphs do not live in.

There is also a standing oddity the doctrine has never priced: base-5 trigrams give
**125 states for 83 glyphs**, leaving 42 unused. That is a lot of slack for a
hand-built enumeration. Base-7 pairs give 49 — too few. Base-7 *triples* give 343 —
far worse. Neither obviously fits better, which is itself informative: **83 is prime,
so it is not a product of digit ranges under any radix**, and any digit construction
must over-generate and truncate. The 125/83 slack is not evidence against base-5; it
is forced by the primality that the whole project rests on.

Since the engine is invariant across all 231 builds (confirmed this session), the
radix is a **fact in the binary**, not an interpretation — and it is cheap to settle
relative to everything else remaining.
